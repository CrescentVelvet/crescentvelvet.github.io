# 2026-11-04

## 殿堂段改用 ANSI 半块女王（峰哥请 GPT 绘制素材）

**起因**：字符画写实女王在 120×40 网格上始终不好看，峰哥改让 GPT 画了一版 ANSI 真彩半块立绘，
110×110 像素（存储为 110 列 × 55 行 `▀▄█` 半块）。方向已验证：真彩图像层比字符格更适合画人物。

### 数据格式
`assets/data/ascii_mv/link_up/queen_ansi.js` → `window.__LU_QUEEN_ANSI`：
110×110 索引图，`alphabet='.0123456789ABCDEFGHIJKLMN'`（0=透明、1=暗核、2..23 为 22 色量化），
逐像素 `rows[y][x]` 一个字符。**保留上下半格原始分辨率，不做降采样**。
⚠️ 索引 0 是透明而非黑色 —— 量化时只对前景取色，背景才不占调色板。

### 渲染方式（关键：不再走字符格）
`luRenderQueen()` 用 5 张离屏 canvas 把索引图按图层预渲染（unit=8 → 880×880），
`render()` 在字符格画完之后 `drawImage` 叠上去，并 `clip` 到 5..32 行避免盖住顶栏与字幕。
分层：披风 / 主体 / 左马尾 / 右马尾 / 头顶饰；马尾与披风绕根部做 ±0.012 rad 摆动（确定性 sin）。
`CCanvas.queen` 只存姿态描述（x/y/width/t/reveal），`clear()` 要置空 —— 否则跳播会残留上一帧角色。

### 时间轴重构
旧版四个 `lu_s6_*` 各自为政（立柱/淬火/双锤/拉远），现在四个入口都转调
`luRoyalSequence(c,t,top,bt,age)`，用**解析时长** 0/4.09/8.26/12.04 作 age 偏移 ⇒
段落边界画面逐格一致（`royal_checks.js` 断言了 4 个边界的 cells 与 queen 完全相同）。
删除旧 `luHallArch/luHallCols/luHallFloor/luHallThrone` 与 `HALL_*` 常量，无残留引用。

  断言含：像素级 seek 一致性、ANSI 不越界覆盖顶栏/字幕、80s 之前 queen 必须为 null、
  0.1s 步长全段确定性与字集/色号合法。
- ⚠️ 旧的 `check_hall.cjs`（16 项）基于已删除的台阶/靠背几何，**已作废**，勿再跑。

### 工具链
`tools/ascii_mv/import_ansi_actor.py`：解析真彩 SGR（只当数据，`\x1b[2J` 之类直接报错不执行），
`▀▄█ 空格` → RGB 像素图；再用 MaxFilter/MinFilter + floodfill 判"封闭暗块"决定透明度，
仅对前景做 22 色中位切分量化。`--preview` 可出 PNG 核对。

### 推镜峰值 77 → 68 格 + 加大飘动（v4）
`luRoyalSequence`：`width=53+close*15`（峰值 68）、`y:5-close*0.5`（原 3.2）。
抬升量必须跟着降：源图内容从 `y=2/110` 起，抬 3.2 行会把**冠冕**先切掉（身份特征），
宁让裙摆下缘入画外。

⚠️ 68 仍不是「全身入画」：人物内容高 `width/2*104/110` = **32.1 行**，画框只有 27 行
（y5–32），仍切脚 **5.2 行（16%，靴子以下）**。真要全身不切需 **≤57 格**（27÷0.945×2）。
`close` 在 89.9–91.65s 恒为 1，故该区间宽度恒定，可直接做同尺寸前后对比。

飘动（`luRenderQueen.part`）：披风 0.012→0.034(+谐波 0.011)、左发 0.012→0.040、
右发 0.015→0.047，另加 `unit` 级横移（披风 1.9、双马尾各 1.0）。原 0.7° 在 24fps 里
几乎看不出风；现值约 2.5°，尾部横向位移 ≈1 格，无发根脱开、无脸遮挡。

断言（`royal_checks.js`，共 **360** 项）：新增 `peak.width<=68`、
`crown inside frame`（`peak.y+peak.width/2*(2/110)>=5`）、
飘动位移 `moved>2000`（0.15s 内 alpha 掩膜变化像素数）。

⚠️ **harness 坑（误判成「重试逻辑坏了」）**：失败文案末尾的 `[重试]` 在 1300×900 窗口里
落在视口外（实测 y=818.6 > vh=808），`elementFromPoint` 返回 null，
`Input.dispatchMouseEvent` 打空 ⇒ 故障 UI 原地不动、数据永不加载。修法：先
`scrollIntoView({block:'center'})` 再取 rect、断言已命中，点后断言 `loadTxt` 不再含 404。
另给本地服务加 `Cache-Control: no-store`（Chrome 会缓存 404，重试拿缓存再失败）。
两处都改在生成链上的 `record_royal.js` / `prepare_royal_retry.cjs`，重跑 prepare 不会丢。

产出 `link_up_queen_ansi_v4.gif`（864×577，397 帧 / 24fps，16.54s，7.4MB）+ v4 接触表；
`royalChecks 360` 全过、`e2e 25/25`、`errors=0`、近重复帧 0。

### 两条腿一黑一白 → 补对称高光（v5）
用户报「两条腿一条黑一条白，是 GPT 生成的误差」。逐像素核对后**数据其实是近似对称**的：
两条腿都是 `#09090b` 黑填充 + `#4c4744/#a29587` 灰描边，大腿带只有左腿多出一条
2~4 px 宽的奶白（`#fdf3c2`）亮带（数据 x 52–56 / y 69–93），缩放后视觉上读成「白丝袜」。
⚠️ 排坑记录：用 `import_ansi_actor.py` 的调色板直方图比较左右腿（y66–85 均值 58.9 vs 60.1）
**看不出差异**，因为差异只在 2~3 列上；靠渲染帧亮度热图（按 4×4 求均值打 ASCII）才定位到
屏幕上 x≈390–400 的长亮带 = 数据 x 53–56，右侧对应位置全暗。
修法：`tools/ascii_mv/patch_queen_legs.py`（以 x=61 为轴，把左腿奶白/灰亮部镜像到右腿，
只覆盖 index 1/18–20，右侧 +1px 加宽抵消 0.4× 降采样稀释；51 px，幂等标记 `legHighlight`）。
奶白 `#fdf3c2` 不满足 `luQueenLayers` 的 gold 判定（`p0 > p2*1.35` 不成立）⇒ 仍在主体层，
不会跟马尾/披风一起摆动。

产出 `link_up_queen_ansi_v5.gif`（864×577，397 帧 / 24fps，16.54s，7.39MB）+ v5 接触表；
`royalChecks 360` 全过、`e2e 25/25`、`errors=0`、近重复帧 0。
⚠️ 录制要带 `START/END/FPS/PXW`：不带参数会跑全曲 0–188s（2229 帧，白跑 5 分钟）。

### 后腿改「填平两条描边之间的空芯」（v6，推翻 v5 的镜像做法）
用户澄清了结构：**画面左侧（她右腿）是一整条奶白；画面右侧（她左腿）是黑腿 +
两条奶白描边，腿本体是两描边之间那 2px 黑**。v5 把其中一条描边当成腿去镜像，
位置落错、白块比前腿还粗，用户否掉是对的。
逐像素复核（`lum > 110` 判亮）：前腿白带 y70–78 宽 2–3 px；后腿两描边间距固定
2–4 px（y70 起 67–69 → y80 的 71–75，斜率 +0.55/行，与前腿 −0.5/行镜像对称）。
⚠️ 只看 index 2/3 会把前腿估窄一半——它视觉宽 4–5 数据 px，相邻 `#a29587`
（亮度 130）也算亮部；这个误判正是 v5 出错的起点。
修法：`tools/ascii_mv/patch_queen_legs.py` 重写为 `fill-gap-v1`——逐行在 x66–78 找
间距 2–4 的两个亮列，**只填它们之间的暗像素**（index 3 `#fdf3c2`），两侧描边原样
保留。共改 **23 px / 11 行 / x67–74 / y70–80**，左腿一个像素未动。
试过两条歧路：① 两侧描边压成近黑（`#09090b`）⇒ 后腿变成一条孤立白线、过细；
② 压成暗暖灰 `#75695a` ⇒ 亮度 117 仍并入白色，反而更粗。
产出 `link_up_queen_ansi_v6.gif`（864×577，397 帧 / 24fps，16.54s，7.35MB）+ v6 接触表；
`ROYAL CHECKS 360` 全过、`e2e 25/25`、`errors=0`、近重复帧 0。

### 后腿仍然偏粗 → 改为「整条按前腿镜像」（v7，再推翻 v6）
用户看了 v6 后指出「右侧还是比左侧粗，得去除奶白描边」，并明确口径：
**左腿什么颜色描边右腿就什么颜色描边，不要压暗**。
量化确认 v6 的问题：y72–80 前腿亮部 2–3 px、后腿 5–6 px（多出的正是两条描边 129/162）。
⚠️ 排坑一：`snap.js` 的本地服务没有 `Cache-Control`，Edge 缓存 `queen_ansi.js`，改完数据
截图看到的还是旧图（已给 html 与 assets 都加 `no-store`）。
⚠️ 排坑二：v13「沿用上一行模板」的兜底让后腿多画了 3 行（渲染高 42 px vs 前腿 31 px），
越改越粗；根因是 v5/v6 遗留的后腿奶白在 y79–81 没被清掉。
⚠️ 排坑三：先按 y60–95 全范围清后腿奶白，误伤了 y63–68 裙腰与发梢（x72–79 那片奶白
是头发不是腿）；改为只在腿区 y69–84 / x65–77 清理。
最终修法：`patch_queen_legs.py` 重写为 `mirror-front-leg-axis62`——取前腿奶白最大连通块
（17 px / x52–56 / y70–78）＋每像素紧邻一列（保留过渡色），以 **x=62** 为轴镜像到后腿；
镜像前先清空后腿区所有非红色亮部（index 1）。共改 59 px，前腿一个像素未动。
幂等：连跑三次字节一致（⚠️ 踩过写回时重复追加 `window.__LU_QUEEN_ANSI=` 前缀和 `;`）。
渲染实测三帧全部对齐：82s 187↔185、85s 188↔188（同 17×31）、91.6s 317↔318（同 22×40）。
产出 `link_up_queen_ansi_v7.gif` + v7 接触表；`ROYAL CHECKS 360` 全过、`errors=0`。
