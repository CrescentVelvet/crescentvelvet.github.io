## 沙盘战争：七八千行单文件是否需要拆分（讨论结论）

用户询问后续独立修改地图、坦克、导弹样式时，模型是否会被迫读取整个 HTML，以及是否应该拆分文件。本次只记录结论，不改代码。

- 后续任务通常可以先按关键词、类名、函数名和稳定边界定位，再读取目标代码段及其依赖；不会默认把七八千行全文一次性塞进上下文。地图可重点读 TerrainRenderer、场景数据、地图容器 CSS；坦克/导弹可重点读对应 UNIT_CLASSES、.unit-* CSS、Projectile/发射逻辑和必要的回归脚本。
- 但“局部读取”不是绝对隔离：单文件里的 HTML、CSS、全局变量、类定义和初始化顺序彼此耦合。若局部改动影响共享 token、层级、坐标、全局状态或事件绑定，仍需要回读相关上下游；复杂任务也可能需要抽查整文件结构。上下文压力主要来自跨模块依赖和反复验证，不是单纯行数。
- 当前不建议立即拆分。现页面是 Jekyll 下的单页 HTML，内联 CSS/JS 依赖全局 DOM、脚本先后顺序、现有探针和本地无构建流程；贸然拆分会增加加载路径、全局命名、部署/Jekyll 相对 URL、调试和回归成本。后续编辑单个模块时，按目标段读取已经够用。
- 如果未来需要长期扩展，建议渐进式拆分：先建立明确的 section 注释与稳定命名（地图样式/地图渲染器、单位样式/单位类、弹丸样式/弹丸类），再考虑只把纯 CSS 拆成一个共享文件；最后才评估把地图渲染器或单位模块拆成 JS 文件，并保留现有全局入口和回归探针。不要为了减少文件行数而拆分。
- 判断触发条件：同一模块频繁修改、多人协作冲突明显、单次任务经常需要跨越数千行、或页面开始出现明确的加载/命名空间问题时，再做拆分设计；拆分前先列出依赖图并跑现有回归。

结论：当前保持单文件，后续按模块定向读取和编辑；先做边界标识与依赖收敛，暂不承担拆分带来的维护成本。


## 本地 Jekyll 起不来的根因：Windows 智能应用控制（SAC）拦了 Ruby 编码扩展

用户 `bundle exec jekyll serve` 一启动就 `[BUG] vm_call_super: should not be reached` + exit 3。
根因**不是 Jekyll、不是 Gemfile、不是 bundle**，是 Ruby 本身在启动阶段就崩：

- Windows 11 26200 专业版，`HKLM\SYSTEM\CurrentControlSet\Control\CI\Policy`
  的 `VerifiedAndReputablePolicyState = 1` ⇒ **智能应用控制处于强制模式**。
- `D:\Ruby34-x64\...\x64-mingw-ucrt\enc\` 下 **61 个 .so 中有 9 个被 SAC 拒绝加载**：
  `enc/{gbk,gb18030,iso_8859_4,utf_16be,windows_1251}.so`、
  `enc/trans/{gbk,gb18030,emoji_sjis_kddi,japanese_euc}.so`。
  其余 52 个（含同样未签名的 `gb2312.so`、`big5.so`）正常 ⇒ SAC 判定不透明。
- 直接加载这些文件返回 **WinError 4551「应用程序控制策略已阻止此文件」**；
  CodeIntegrity/Operational 日志有对应 3077「did not meet the Enterprise signing level requirements」。
- 崩溃链：进程 locale 为 CP936 ⇒ Ruby 启动时 `Encoding.find("GBK")` ⇒ 该 .so 被拒
  ⇒ Ruby 内部对"加载失败"处理有缺陷（`vm_call_cfunc/ vm_call_super cfp consistency error`）⇒ rb_bug 崩溃。
  `File.read`/`File.write` 等**构造系统异常**的动作会再踩一次同一坑 ⇒ 崩在
  `rubygems/defaults/operating_system.rb:5` 的 `File.write(checkfile, "")`。

**关键实验**：同一份 `gbk.so` 换个目录/换个名字就能正常加载，只有**原路径**被拦 ⇒
SAC 记录的是完整文件路径。实测把 Ruby 整目录复制到 `D:\_rubytest2` 后，
9 个文件全部加载成功，`ruby test.rb` exit 0 正常抛出 `Errno::ENOENT`，问题消失。

修复方向（未执行，等用户决定）：① 关闭智能应用控制（**不可逆，重装系统才能再开**）；
② 重装 Ruby 到新路径（实测有效）；③ `chcp 65001` **无效**（已实测，非此因）。
诊断残留已清理，`D:\Ruby34-x64` 未改动。

### 已落地修复：原地重建文件解除 SAC 拦截（2026-10-24 实测有效）

在诊断基础上找到**不改注册表、不重装 Ruby** 的修复法：**原地重建被拦文件**
（备份 → `os.remove` → 从备份 `copy2` 写回）。新写入的文件不在 SAC 旧的路径哈希
清单里，重新评估后放行。`ctypes.WinDLL` 直接加载从 FAIL 4551 变 OK，可逐文件验证。

执行结果：
- `enc/` 下 9 个（gbk、gb18030、iso_8859_4、utf_16be、windows_1251 +
  trans/{gbk,gb18030,emoji_sjis_kddi,japanese_euc}）已修复；
- 后续 `jekyll build` 又暴露 **`lib/ruby/3.4.0/x64-mingw-ucrt/etc.so` 同样被拦**
  （报错伪装成「tzinfo 未安装」，真实信息 `4551: ...etc.so`）⇒ 说明拦截**不限于 enc/**，
  必须全量扫描 `lib/` 下所有 .so。修复后共 99 个 .so 复扫零失败。

端到端验证：`bundle exec jekyll build --config _config.yml,_config.dev.yml` **exit 0，约 10.4s**；
`jekyll serve` 正常起在 `http://127.0.0.1:4000/`。原始 `[BUG] vm_call_super` 崩溃彻底消失。

固化为脚本 `tools/fix_sac_blocked_ruby.py`（扫描 + `--dry-run` + 备份到临时目录 + 逐文件复验），
可复用于 SAC 再次误拦。**仅重建文件内容相同，未改任何 Ruby 代码或版本。**

⚠️ 遗留提示：SAC 仍处强制模式，将来 Ruby 升级/重装后可能再次误拦 ⇒ 复发就跑该脚本。
另 `jekyll -v` 单独跑会报 `rexml 3.4.4 vs Gemfile 3.4.1` 冲突，用 `bundle exec` 即可，与此无关。
