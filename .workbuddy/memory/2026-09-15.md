- `assets/css/main.scss` 引了 `vendor/font-awesome/{fontawesome,solid,brands}` ⇒ **全量编译进 main.css**，

### 卡片尺寸的准确算式（以后改标签/字号照这个算）
内容盒需求 = 图标盒 16 + 图标右距 4 + letter-spacing 1 + 最长标签 85 = **106px**
（最长标签是 5 汉字"大模型对话"/"数据库解析"；16px 字号下汉字步进就是 16px，5×16 + 5×1 = 85，很稳定）

### ⚠️ 测量工具的坑（踩过一次，白折腾一圈）
**不要用"克隆一个 shrink-to-fit 元素量自然宽"来求卡片需要多宽 —— 会严重低估。**
克隆法给出 94.25px，而按部件累加（图标 16 + 距 4 + ls 1 + 文本 85）= 106px，
且 850px/6 列时"内容盒 105px < 106px ⇒ 换行"的预测与实际完全吻合 ⇒ **部件累加法才对**。
正确做法：`Range.selectNodeContents(文本节点)` 后把 `getClientRects()` 的宽度**逐段相加**
（不能用 rects.length>1 当换行判据的同时又用宽度，换行时宽度会变成单行最宽，反而变小）。
同一次错误的克隆法还让我把 960~1200px 的余量误报成 13.75px（真值 2px）。
**教训：余量这类结论必须有两个独立方法交叉验证，或者用"换个参数看是否真的换行"来反证。**

### ⚠️ 布局无损的换算技巧（以后改卡片描边可直接照抄）
给卡片加 1px 描边会吃掉内容盒 2px（`box-sizing: border-box`），有掉列风险。
把横向 padding 从 8px 改成 7px、纵向 14→13px 即可**完全抵消**：
横向合计 7+1=8、纵向 13+1=14，与原来一致 ⇒ 卡片外框尺寸、内容盒宽度、卡高（52px）全部不变，
上面那套列数算式一个字都不用改。实测确认：13 个视口的列数与卡宽与改动前**完全相同**。

### 波纹的架构改动（行为变更，非纯视觉）
原来：挂在视口级 `#ripple-container`（`position:fixed` 铺满视口）+ 固定 200px + 纯黑 10%。
问题：卡片宽仅 124px、高 52px，固定直径无法适配；而且容器铺满视口 ⇒ 圆会**溢出卡片洒在白底页面上**。
实心绿按钮时代看不出来，描边卡片上一眼就是脏色。
现改为：
- 波纹挂在**卡片内部**（`<a>` 上），卡片 `position:relative; overflow:hidden` 负责裁切（含圆角）。
- 直径 = **点击点到卡片四角的最远距离 ×2**（`Math.hypot` 四次取 max），任意落点都"刚好铺满就消失"。
- 位置要扣 `clientLeft/clientTop`：绝对定位子元素的原点是 **padding box**，不是 border box。
- 颜色 `--ripple-color` = `rgba(82,173,200,0.20)`（跟 accent 走）。
- 删掉 `#ripple-container` 的 CSS 与 DOM；`pointerdown` 里加 `e.target.closest('.link-button')` 判空，
  落在卡片缝隙里不再出波纹。
- 保留原有的三条 P1 修复成果（只挂 pointerdown / 提前到 pointerdown / 限定在 .button-grid 内）。

### ⚠️ 像素级差分的两个坑（**都真踩了，各误报一次**）
要证明"波纹被裁在卡片内"，我用 CDP 截图 + 逐像素差分。前两次判据都是错的：
1. **数"页面上符合强调色的像素"** ⇒ 误报 723 个"泄漏"。实际是**页脚本来就有蓝色元素**
   （GitHub 图标周边），与波纹无关。教训：任何"按颜色在全图里找"的判据都会被页面固有元素污染。
2. **拿"鼠标移入前"当基线** ⇒ 误报 34195 个。实际是 **hover 的 `box-shadow: 0 3px 10px`**
   本来就画在卡片外（约 13px），它也是"变化像素"。教训：基线与对照帧之间**只能差被测的那一个变量**。
3. 正确做法：**按下鼠标 → 等 380ms 拍 A → 只把波纹节点删掉、保持 hover+active 不变 → 拍 B**，
   A/B 之差就纯粹是波纹。结果：变化像素包围盒 x1547~1752 / y330~429，
   卡片允许区 x1506~1789 / y326~434 ⇒ **卡外 0 个变化像素**，结论无歧义。
   取证日志要把"包围盒"和"允许区"都打出来，否则失败时无法判断是真泄漏还是判据错。

### ⚠️ 写这种测试另外三个坑
- **`getBoundingClientRect()` 含 transform 的动画进度**。量波纹"设定的直径"必须读
  `getComputedStyle(node).width`（布局宽）；读 rect 在 120ms 时只有设定值的 ~20%，会误判成"直径不对"。
- **卡片是真 `<a>`，`mouseReleased` 会导航**，后续用例全找不到元素（报
  `Cannot read properties of undefined`）。在捕获阶段 `addEventListener('click', e=>e.preventDefault(), true)`
  拦掉默认行为即可，波纹依赖的是 `pointerdown`，不受影响。
- **`pngstat.js` 的 `decodePNG(file)` 收的是文件路径**，不是 Buffer（传 Buffer 会被当成路径报
  `ERR_INVALID_ARG_VALUE: ... null bytes`）。返回的是 `{width,height,ch,data}`，像素在 `data` 且要按 `ch` 跨步。

### ⚠️⚠️ 空页头的坑：不能删 `#site-nav`，会无限递归
`assets/js/main.min.js`（131KB 压缩 bundle）里的 greedy-nav 初始化**没有守卫**：
```js

$(window).resize(function(){updateNav()}), $btn.on("click",...), updateNav(),   // ← 无条件调用

```

## 高光改为「整片光场」（commit f836240，未 push）

用户观察到："一个按键有跟随高光，周边按键也应该有跟随高光，参考 Apple 的光效"。

### 设计判断（**这是本轮的核心，比代码重要**）
原实现是**每张卡各自的开关**：`:hover` 时 `background-image` 出现，非悬停卡完全没有光。
视觉上就是 19 个各自为政的小部件 —— 各自亮、互不相关。
Apple 那类效果的实质是**一个位于光标处的虚拟光源照亮整片表面**，强度按距离衰减：
光标下的最亮、邻卡依次减弱，读起来像"同一盏灯洒在一排图标上"。

改法（三处，都很小）：
1. 渐变从 `:hover` **移到基类** `.link-button`，强度由 `--glow`(0~1) 决定。
2. JS 按"卡片中心到光标的距离"给**范围内的每张卡**写 `--mx/--my/--glow`，超出半径写 0。
3. `:hover` 只管"选中反馈"：描边转强调色、底色微亮、上浮、投影、倾斜。

**关键约束：非悬停的邻卡只被点亮，绝不改描边/底色/位移。**
否则"我马上要点哪张"的指示就被糊掉了 —— 这是可用性底线，不是审美偏好。

**光的局部坐标必须逐卡算**（`--mx = 光标x − 该卡.left`）。同一光源落在左邻卡上是它的**右**半边，
落在上邻卡上是**下**半边 —— 正是这个方向差异构成"单一光源"的错觉。
实测：左邻卡 `--mx=225.4`（卡宽 138.3，>69.2 ✓）、上邻卡 `--my=95.8`（卡高 52，>26 ✓）。

### 参数（都在 `:root`，改这里即可）
| 变量 | 值 | 作用 |
|---|---|---|
| `--spot-alpha` | 0.22 | 光标正下方那张的上限强度 |
| `--spot-size` | 160px | 单张卡内高光的渐变半径 |
| `--glow-radius` | 340px | 衰减半径（JS 读它） |
| `--tilt` | 4deg | 最大倾角（JS 读它） |
衰减用 `(1-t)²`：在半径处平滑归零、无硬边。
实测一屏的亮度分布：`2px→0.999  70→0.63  140→0.345  156→0.292  171→0.246  210→0.146  313→0.007`，
共点亮 11/19 张。**注意网格是各向异性的**（横向节距 157.5px、纵向 70px），
所以等距衰减下纵向铺得比横向远 —— 这是物理正确的，不是 bug。
`GLOW_MIN = 0.004` 是"太暗就别写"的门槛，实际截止在半径的 ~0.92 处。

### ⚠️ `calc()` 里的自定义属性必须保证有值（IACVT 陷阱）
`background-image` 里用了 `calc(var(--spot-alpha) * var(--glow) * 100%)`。
未注册的自定义属性若**缺失**，`var()` 替换失败会让整条 `background-image` 变成
invalid-at-computed-value-time ⇒ 退回 `none` ⇒ **卡片连渐变层都没有**。
所以注册了：
```css
@property --glow { syntax: '<number>'; inherits: true; initial-value: 0; }
```
`initial-value` 保证即使 JS 从不写它也是确定的 0；`.link-button` 里再补一句 `--glow: 0` 兜底老浏览器。
**教训：把自定义属性放进 `calc()`/`color-mix()` 之前，先确认它一定有值。**
透明度用 `color-mix(in srgb, var(--accent) N%, transparent)` 从 `--accent` 派生，不再抄一遍 RGB。

### ⚠️ 逐元素"读-写-读-写"会逐张触发样式重算
`paint()` 要给最多 11 张卡写 3 个自定义属性。若写成 `取一张卡->算->写->取下一张`，
每次写都让样式变脏，下次 `getBoundingClientRect()` 就得刷一次 —— N 张卡就是 N 次样式重算。
改成**先把 19 个矩形一次性读完（boxes 数组），再统一写**，每帧最多刷一次。
另外只把"上一帧亮、这一帧灭"的卡归零，不每帧写满 19 张。

### 性能实测（`perf_glow.js`，新）

### 写这类测试踩的三个坑
1. **实现里有内部门槛时，别断言"朴素边界"。** 我一开始断言"不亮的卡距离 ≥ --glow-radius(340)"，
   实测失败：最近的不亮卡在 320.3px。因为 `GLOW_MIN=0.004` 让实际截止提前到半径的 ~0.92 处。
   → 改成两条**与实现常量无关**的性质断言：`min(不亮距离) > max(点亮距离)`，
   且 `max(点亮距离) ∈ [0.85R, R]`。这样门槛怎么调都不会误报。
2. **有元素被 transform 时，同排/同列要用容差匹配。** 我原来写 `r.top === self.top`，
   但悬停卡被 `translateY(-2px)` + 倾斜，它的 `rect.top` 偏了 ~2px ⇒ 精确比浮点全部匹配失败
   （表现为断言被静默跳过，只打了一行"[提示] 未找到"）。改成按中心比较 + 6px 容差。
3. **悬停目标要挑"四邻齐全"的。** 我最初用第 3 张卡做光场用例，它在**第一行**，本来就没有上方邻卡，
   方向性断言永远拿不到对象。改用第 10 张（7 列布局下第 2 行第 4 列）。
