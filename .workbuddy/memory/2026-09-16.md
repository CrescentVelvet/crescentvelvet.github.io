## diary_tree.html 加密方案安全审计（grill-me，进行中）

### 已核事实（file:line 均已验证）
- 解密入口 `_pages/diary_tree.html:2116`：`CryptoJS.AES.decrypt(ciphertext, password)`——口令式 OpenSSL 格式。
- 密文格式实测：`U2FsdGVkX1` → `Salted__` + 8 字节盐（`assets/data/2005-07.txt` 首 240 字符），即 OpenSSL `enc` 兼容格式。
- `assets/js/crypto-js.min.js` 反解：
  - EvpKDF 默认 `keySize:4, hasher:MD5, iterations:1`（≈ OpenSSL EVP_BytesToKey MD5×1）。
  - `t.kdf.OpenSSL.execute`：盐 8 字节随机，key||iv 由 EvpKDF 派生（AES-256 → keySize 8）。
  - AES keySize 8（256-bit），模式 CBC（`SerializableCipher` 默认）。
- 数据面：`assets/data/` 134 个 .txt，共 32.95 MB（平均 246 KB/文件）。
- 加载面：`runPool` 并发 6（diary_tree.html:2104-2141），逐文件 fetch → AES.decrypt → parse；密码错误靠「空串/解析 0 条」判定（2145-2154）。
- 无 localStorage/sessionStorage/缓存；每次刷新全量重解密。

### 风险定性（待与用户逐条确认）
1. **KDF 是最大的洞**：MD5×1 无迭代。hashcat -m 11500 在单张现代 GPU 上 ~2-5 GH/s：
   8 位小写+数字口令 ≈ 24 分钟跑完；常见字典秒级。AES-256-CBC 本身没问题，问题全在口令→密钥这一步。
2. 明文依赖：密码在 JS 里明文可用（前端解密的固有属性，不可修，只能靠 KDF 加慢）。
3. HTTPS 下无中间人明文泄露；但 GitHub Pages 场景代码与密文同源公开。
4. 手机端慢的根因：CryptoJS 是纯 JS 实现（无 WASM/原生），32.95 MB 密文 + JS AES 在移动端是数百 MB 级内存分配（WordArray），GC 压力大。

## grill-me 定案（五分支全部闭环，2026-09-16 上午）

1. **威胁模型**：熟人 + 拿到密文的认真攻击者。KDF 必须 PBKDF2-HMAC-SHA256 ≥60 万迭代（OWASP 2023 线）。
2. **格式迁移**：一次性迁移。本地 Node 脚本全量重加密，页面只认新格式，旧 CryptoJS 解密路径删除。迁移时**顺手换新口令**。
3. **加载架构 C1**：manifest 纯聚合索引（年/月/日的字数·条数·分类计数·hasEntries 标志，正文一字不放），解锁只解 manifest（几 KB），日详情按需解单月正文（平均 246KB）。首屏解密量 33MB → 几 KB。
4. **混合加密**：随机 256-bit DEK 加密全部数据，口令只做 PBKDF2 信封包裹（`key.envelope`）。换口令 = 毫秒级 rewrap。口令基线 ≥14 位随机（不分叉，直接拍）。
5. **工具链**：`tools/encrypt_diary.js`，零依赖（Node 内置 crypto），子命令 encrypt / rewrap / migrate；明文目录加 .gitignore 永不进 git。
6. **git 历史不清理**：旧密文+旧口令作废成无害化石，不 rewrite history、不 force push（符合用户铁律）。

### 实施注意（从 grill 过程中沉淀）
- 新格式定：PBKDF2(600k, SHA-256) → 解信封得 DEK → WebCrypto AES-256-GCM 解数据（顺手获得完整性校验，替代无认证的 CBC）。
- 单月按需解密预计手机 200-500ms，串行即可；若实测慢再谈按日分块流式（不过度设计）。
- manifest 聚合统计 = parseDecryptedText 在 Node 侧预跑一遍（分类/字数逻辑与页面 classifyEntry/wordCount 对齐，避免两处口径漂移）。
- 回归验证：dev 链路 make_dev.js 要适配「manifest+按需解密」的新解锁流程（原 unlock handler 整段替换的正则要改）。
- 副产物风险：`window.files` 列表本身泄露「哪些月份有日志」的元数据 → manifest 化后文件名可改无信息量序号，待实施时定。

### 修正后的架构（浏览器端闭环版，待确认）
- 共享模块 `/assets/js/diary-crypto.js`（WebCrypto）：解信封得 DEK、按需解密、加密导出（强制新随机 IV）。
- `assets/data/key.envelope`（几 KB，口令 PBKDF2 包裹 DEK）三页共用；换口令=导出新 envelope 一个文件。
- enc_reader：解密阅读+编辑+重加密导出（DEK 已在内存，重加密不用再输口令）+「换口令」按钮。
- text_processor：格式化+加密导出（fetch envelope 解 DEK，多等 0.5-1s KDF）。
- manifest：预计百 KB 级（~2000 天 × 日字数/条数/分类位图），非"几 KB"；解决的是 33MB 下载账（GitHub Pages 缓存仅 10 分钟），WebCrypto 只解决计算账。
- 维护机制（待拍板）：写入路径自动顺带导出更新后的 manifest（放 2 个文件）+ diary_tree 安全网（window.files 有而 manifest 缺的月份当场 fetch 解密合并）。
- ⚠️ rewrap 不换 DEK ⇒ 旧口令持有者拿 git 历史里的旧 envelope 仍能解当前数据；真要踢出旧口令需「深度轮换」按钮全量重加密（桌面端操作，罕见场景）。
- innerHTML 直注密文 HTML → 迁移时顺手改结构化渲染（自加密内容，无现实 XSS，但求稳）。

### 10:55 最后两项定案
- **manifest 维护 = A+B 混合**：enc_reader/text_processor 加密导出时同时导出更新后的 manifest（放回 2 个文件）；diary_tree 解锁后对比 window.files，发现 manifest 缺的月份当场 fetch 解密合并兜底。
