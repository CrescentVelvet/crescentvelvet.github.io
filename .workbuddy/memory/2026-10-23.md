## 2026-10-23 补：侧 45° 头发/眼睛出现蓝绿雾块

峰哥反馈：侧 45° 下眼睛和头发有蓝绿小区域，SuperSplat 没有。

### 先排除的（都有实测数据）
1. **不是背景 clearColor**：ROI 统计，clearColor 换 #222222/#000000/#ffffff，
   头发 ROI 的显著蓝绿像素 = 0，meanRGB 几乎不变（131,101,91）⇒ 与 clearColor 无关。
2. **不是 SH 高阶项**：degree 0/1/2/3 扫描（正 45°、d=0.55，头发 ROI）：
   blue%=0、green%=0 全档一致；meanRGB 129-131 / 101-102 / 90-91，差异 ≤2。
   逐像素差：deg3 vs deg0 mean|d|=4.56、23.9% 像素 >6，方向是 **ΔR -0.4 / ΔG -1.7 / ΔB -3.6**
   ⇒ SH 让画面**更暗更暖**，不产生蓝绿。band3 单独贡献 mean|d|=2.19。
3. **不是 eigen 丢弃单独造成**（见下，虽是真 bug 但不是雾块主因）。

### 根因：`antialiased: true` 的透明度补偿
库 L8404-8411：
```glsl
float detOrig = det(cov2D);
cov2D += 0.3;                       // 这一行 antialiased=false 时也执行
float detBlur = det(cov2D);
vColor.a *= sqrt(max(detOrig / detBlur, 0.0));   // ← 只有 true 才执行
```
眉毛/发丝/眼缘由 detOrig 极小的 splat 构成 ⇒ 补偿系数可低到 0.1~0.3 ⇒ 这些区域被
「掏成半透明」⇒ 透出**背后的冷色背景**（灰蓝天空、灰建筑）⇒ 蓝绿雾块。
SuperSplat 背景是暖色夕阳，同样透出也偏暖 ⇒ 不易察觉（不是它没有这个机制：
PlayCanvas `gsplatCorner.js` 里 `GSPLAT_AA` 的 aaFactor 公式与本库**完全相同**，也是 sqrt）。

定案 **`antialiased: false`**（模糊保留、只不降 alpha）。A/B 视觉：AA on 眉毛周围大片灰蓝雾；
AA off 干净暖棕。四机位（0°/45°/45°远/90°）复验全部干净，fps 60.4，零异常。

### 顺带修掉的真 bug：`LOCAL PATCH (eigen clamp)`
上游 `term2 = sqrt(max(0.1, mid²-D))` 把下限加在**判别式**上 ⇒ term2 ≥ 0.316 ⇒
小 splat 的 eigenValue2 变负 ⇒ 被 `if (eigenValue2<=0) return;` **丢弃**。
3DGS 官方 / PlayCanvas 都是 `lambda2 = fmax(mid - radius, 0.1)`（下限加在 λ2 上）⇒ 保留。
改后：整图 89% 像素变化（补回被丢弃的小 splat，画面更实），但**不解决雾块**（雾块是 AA 造成）。

⚠️ 踩坑：写 GLSL 注释时用反引号包了代码片段，把模板字符串提前终止 ⇒
`node --check` 报 SyntaxError，页面里 `window.__debugGroupXform is not a function`。
**GLSL 注释里禁止出现反引号**。

### 回归
`check_splat_compare.js` 全过 / `verify_render_parity.js` 10/10 / `unify_semantics.js` 26/26；
补丁标记：degree 3 = 15、sort gate = 1、eigen clamp = 1。

## 高斯对比（_pages/splat-compare.html）
- 库级（gaussian-splats-3d v0.4.7 + three r185）：**必须 `gpuAcceleratedSort:false`**（否则黑屏）、**`antialiased:false`**（见下条，10-23 定案）、**`sphericalHarmonicsDegree:3`**（0 = 丢视角相关色；band3 占 SH 能量 54.68%、色差 RMS 9.7%，代价 +1.6s/百万 splat、+48MB）；**变换必须放 splatGroup 级**（改 scene0 无效）。
- ⚠️ **`antialiased` 必须 false**（10-23 定案，推翻 09-12 旧结论）：true 时库会 `cov2D += 0.3` 后 `vColor.a *= sqrt(detOrig/detBlur)`。薄层/微小 splat（眉毛、发丝、眼缘）detOrig 极小 ⇒ 补偿系数低到 0.1~0.3 ⇒ 半透明掏空，透出背后**冷色背景**（灰蓝天空/建筑）⇒ 侧 45° 头发与眼睛出现**蓝绿雾块**（SuperSplat 因背景是暖色夕阳而不易察觉）。false 时**仍然 +0.3px 模糊**（抗走样保留），只不压低不透明度。09-12「关掉会增黑斑 30~45%」是 16bit 排序时代的误判（`blob_scan.js` 会把变实的眉毛/发丝也算成暗斑）。
- ⚠️ **degree 3 靠本地补丁**（上游 shader 只有 degree 1/2）：**15 处 `LOCAL PATCH (degree 3)`**（`grep -c` 应为 15），7 个逻辑点：`decode…SectionHeader`（补 `>=15 → 3`，最隐蔽）/ `INRIAV1PlyParser` 两路径 / `fillSphericalHarmonicsArray` / **`writeSplatDataToSectionBuffer` 两分支**（最易漏：buffer 按 45 分配但后段不写、零报错）/ GLSL（`SH_C3`+`sh9..15`+采样，须用 `maxSphericalHarmonicsDegree>=3` 编译期开关包住并留在 degree-2 作用域内）/ 纹理打包（45→**48**，不是 46）。**升级 vendor 必须重新应用全部**（另有 `sort gate` 1 处、`eigen clamp` 1 处，`grep -c` 各应为 1）。
- 相机 **fov = 60**（峰哥 2026-10-20 拍板，故意不跟 SuperSplat 默认 85）。
- **`splatSortDistanceMapPrecision: 20`**（默认 16）+ **重排门限补丁**（`LOCAL PATCH (sort gate)`：上游 `angleDiff<=0.99`=8.11° → `0.9999619`=0.5°；SuperSplat 是 eps 0.001≈0.06°）。二者分别是「随视角漂移的黑斑/白点」与「每 8° 跳一下」的根因。
- **`LOCAL PATCH (eigen clamp)`（10-23，1 处）**：上游把 0.1 加在**判别式**上（`max(0.1, mid²-D)` ⇒ `term2 ≥ 0.316`），小 splat 的 `eigenValue2` 变负、被 `if (eigenValue2<=0) return;` **直接丢弃**；3DGS 官方与 PlayCanvas 都是把下限加在 **λ2 本身**（`fmax(mid-radius, 0.1)`）⇒ 小 splat 保留并抬到最小尺寸。本仓已改成后者。⚠️ 写 GLSL 注释时**禁止出现反引号**（模板字符串会提前终止，`node --check` 才报错，页面表现为探针函数凭空消失）。
- **为什么是 20、为什么不学密度分位**（2026-10-20 量化定案，`.workbuddy/tmp/sortkv.js` 可复跑）：PlayCanvas 也是 `Math.min(20, round(log2(n/4)))`，**20 是双方共同上限**；712k splat 时它用 17 bit（131k 桶），本库 20 = 1.05M 桶（8 倍）。实测「桶内深度跨度/splat 尺度」：均匀 16 = 0.574、17 = 0.281、**20 = 0.030**、canvas 17 分位 = 0.059 ⇒ **20 均匀比 SuperSplat 实际配置细一倍**。⚠️ 本库排序在 **WASM 二进制**里（`sortIndexes`，无 C 源码），JS 只能传 `1<<precision` 一个标量，**做不了直方图分位**，要做得弃用 vendor 排序自己写。⚠️ 未来 4M+ splat 时 canvas 会自动升到 19–20 bit，本库被钳死 20 ⇒ 差距那时才显出来。
- ⚠️ 复现「远/中景才有」的渲染问题：**先把相机拉到用户实际观察距离**（脸 ~120px，d≈1.2）再测。近景 d≤0.55 时 splat 投影大、深度分布陡，量化误差打不乱可见顺序，**A/B diff 恒为 0**（本轮因此在错误候选上多绕很久）。
- **渲染参数基线 = SuperSplat 默认值**：`antialias:false / depth:false / stencil:false / powerPreference:'high-performance'`、`NoToneMapping + exposure 1`、fov 85（本页取 60）、`far 1000`、`halfPrecisionCovariancesOnGPU:false`、`setPixelRatio(devicePixelRatio)`。**故意不一致**：背景 `#222233`（纯黑糊掉暗部，峰哥拍板）。**库硬限**：SH bands 3→2、WebGPU→WebGL2、无 stochastic alpha。⚠️ `fitAllToFirst` 的固定距离 4 是按 fov 65 调的。

## splat-compare 内存释放链核查（峰哥问：删模型/重置后内存不显著下降，反复加删会不会爆）

**结论：不是泄漏，是四层「延迟归还」叠加；不会线性爆。** 两处小缺陷已记入 MEMORY.md。

释放链（已逐行走读）：
- `removePanel`（L339-348）：`p.viewer.dispose()`（= Viewer.dispose，库 L13932，**async、未 await**，finally 里才真正清）+ `p.renderer.dispose()` + `p.el.remove()` + splice。
- `loadPlyToPanel` 换模型（L471-477）：`splatGroup.dispose()` + `renderer.dispose()`。
- 库里 dispose 覆盖：SplatMesh geometry/material/**数据纹理**/splatTree（L10087-10178）、sortWorker **terminate**（L13779，WASM 随 worker 释放）、splatTreeWorker terminate（L9267）、controls/sceneHelper/renderer 引用清空。

不降的四个原因：
1. `renderer.dispose()`（three r185 L17068）**不调 forceContextLoss** —— WebGL context 要等 canvas 被 GC 才销毁，每个滞留 context 白占显存；快速反复加删可能撞 Chrome 单域 ~16 context 上限（最老被强丢→黑屏）。
2. V8 惰性 GC：大 TypedArray 变垃圾后要等 major GC，且堆页常保留在进程（RSS 不降）。
3. GPU 进程显存缓存，任务管理器看不到即时下降。
4. `Viewer.dispose()` 等 sortPromise settle 才 finally 清理（秒级延迟）。

真实缺陷（小）：
- ⚠️ 加载失败分支（catch, L718 起）**漏 `URL.revokeObjectURL(url)`**（成功路径 L717 有）→ 每失败一次漏一个文件大小的 blob。
- ⚠️ renderer 未 `forceContextLoss()`（见上）。

验证方法：DevTools Memory 手动 GC 后对比 heap snapshot；`performance.memory.usedJSHeapSize`；chrome://gpu。
