## 2026-10-23 补：侧 45° 头发/眼睛出现蓝绿雾块

峰哥反馈：侧 45° 下眼睛和头发有蓝绿小区域，SuperSplat 没有。

### 先排除的（都有实测数据）
1. **不是背景 clearColor**：ROI 统计，clearColor 换 #222222/#000000/#ffffff，
   头发 ROI 的显著蓝绿像素 = 0，meanRGB 几乎不变（131,101,91）⇒ 与 clearColor 无关。
2. **不是 SH 高阶项**：degree 0/1/2/3 扫描（正 45°、d=0.55，头发 ROI）：
   blue%=0、green%=0 全档一致；meanRGB 129-131 / 101-102 / 90-91，差异 ≤2。
   逐像素差：deg3 vs deg0 mean|d|=4.56、23.9% 像素 >6，方向是 **ΔR -0.4 / ΔG -1.7 / ΔB -3.6**
   ⇒ SH 让画面**更暗更暖**，不产生蓝绿。band3 单独贡献 mean|d|=2.19。
3. **不是 eigen 丢弃单独造成**（见下，虽是真 bug 但不是雾块主因）。

### 根因：`antialiased: true` 的透明度补偿
库 L8404-8411：
```glsl
float detOrig = det(cov2D);
cov2D += 0.3;                       // 这一行 antialiased=false 时也执行
float detBlur = det(cov2D);
vColor.a *= sqrt(max(detOrig / detBlur, 0.0));   // ← 只有 true 才执行
```
眉毛/发丝/眼缘由 detOrig 极小的 splat 构成 ⇒ 补偿系数可低到 0.1~0.3 ⇒ 这些区域被
「掏成半透明」⇒ 透出**背后的冷色背景**（灰蓝天空、灰建筑）⇒ 蓝绿雾块。
SuperSplat 背景是暖色夕阳，同样透出也偏暖 ⇒ 不易察觉（不是它没有这个机制：
PlayCanvas `gsplatCorner.js` 里 `GSPLAT_AA` 的 aaFactor 公式与本库**完全相同**，也是 sqrt）。

定案 **`antialiased: false`**（模糊保留、只不降 alpha）。A/B 视觉：AA on 眉毛周围大片灰蓝雾；
AA off 干净暖棕。四机位（0°/45°/45°远/90°）复验全部干净，fps 60.4，零异常。

### 顺带修掉的真 bug：`LOCAL PATCH (eigen clamp)`
上游 `term2 = sqrt(max(0.1, mid²-D))` 把下限加在**判别式**上 ⇒ term2 ≥ 0.316 ⇒
小 splat 的 eigenValue2 变负 ⇒ 被 `if (eigenValue2<=0) return;` **丢弃**。
3DGS 官方 / PlayCanvas 都是 `lambda2 = fmax(mid - radius, 0.1)`（下限加在 λ2 上）⇒ 保留。
改后：整图 89% 像素变化（补回被丢弃的小 splat，画面更实），但**不解决雾块**（雾块是 AA 造成）。

⚠️ 踩坑：写 GLSL 注释时用反引号包了代码片段，把模板字符串提前终止 ⇒
`node --check` 报 SyntaxError，页面里 `window.__debugGroupXform is not a function`。
**GLSL 注释里禁止出现反引号**。

### 回归
`check_splat_compare.js` 全过 / `verify_render_parity.js` 10/10 / `unify_semantics.js` 26/26；
补丁标记：degree 3 = 15、sort gate = 1、eigen clamp = 1。

## 高斯对比（_pages/splat-compare.html）
- 库级（gaussian-splats-3d v0.4.7 + three r185）：**必须 `gpuAcceleratedSort:false`**（否则黑屏）、**`antialiased:false`**（见下条，10-23 定案）、**`sphericalHarmonicsDegree:3`**（0 = 丢视角相关色；band3 占 SH 能量 54.68%、色差 RMS 9.7%，代价 +1.6s/百万 splat、+48MB）；**变换必须放 splatGroup 级**（改 scene0 无效）。
- ⚠️ **`antialiased` 必须 false**（10-23 定案，推翻 09-12 旧结论）：true 时库会 `cov2D += 0.3` 后 `vColor.a *= sqrt(detOrig/detBlur)`。薄层/微小 splat（眉毛、发丝、眼缘）detOrig 极小 ⇒ 补偿系数低到 0.1~0.3 ⇒ 半透明掏空，透出背后**冷色背景**（灰蓝天空/建筑）⇒ 侧 45° 头发与眼睛出现**蓝绿雾块**（SuperSplat 因背景是暖色夕阳而不易察觉）。false 时**仍然 +0.3px 模糊**（抗走样保留），只不压低不透明度。09-12「关掉会增黑斑 30~45%」是 16bit 排序时代的误判（`blob_scan.js` 会把变实的眉毛/发丝也算成暗斑）。
- ⚠️ **degree 3 靠本地补丁**（上游 shader 只有 degree 1/2）：**15 处 `LOCAL PATCH (degree 3)`**（`grep -c` 应为 15），7 个逻辑点：`decode…SectionHeader`（补 `>=15 → 3`，最隐蔽）/ `INRIAV1PlyParser` 两路径 / `fillSphericalHarmonicsArray` / **`writeSplatDataToSectionBuffer` 两分支**（最易漏：buffer 按 45 分配但后段不写、零报错）/ GLSL（`SH_C3`+`sh9..15`+采样，须用 `maxSphericalHarmonicsDegree>=3` 编译期开关包住并留在 degree-2 作用域内）/ 纹理打包（45→**48**，不是 46）。**升级 vendor 必须重新应用全部**（另有 `sort gate` 1 处、`eigen clamp` 1 处，`grep -c` 各应为 1）。
- 相机 **fov = 60**（峰哥 2026-10-20 拍板，故意不跟 SuperSplat 默认 85）。
- **`splatSortDistanceMapPrecision: 20`**（默认 16）+ **重排门限补丁**（`LOCAL PATCH (sort gate)`：上游 `angleDiff<=0.99`=8.11° → `0.9999619`=0.5°；SuperSplat 是 eps 0.001≈0.06°）。二者分别是「随视角漂移的黑斑/白点」与「每 8° 跳一下」的根因。
- **`LOCAL PATCH (eigen clamp)`（10-23，1 处）**：上游把 0.1 加在**判别式**上（`max(0.1, mid²-D)` ⇒ `term2 ≥ 0.316`），小 splat 的 `eigenValue2` 变负、被 `if (eigenValue2<=0) return;` **直接丢弃**；3DGS 官方与 PlayCanvas 都是把下限加在 **λ2 本身**（`fmax(mid-radius, 0.1)`）⇒ 小 splat 保留并抬到最小尺寸。本仓已改成后者。⚠️ 写 GLSL 注释时**禁止出现反引号**（模板字符串会提前终止，`node --check` 才报错，页面表现为探针函数凭空消失）。
- **为什么是 20、为什么不学密度分位**（2026-10-20 量化定案，`.workbuddy/tmp/sortkv.js` 可复跑）：PlayCanvas 也是 `Math.min(20, round(log2(n/4)))`，**20 是双方共同上限**；712k splat 时它用 17 bit（131k 桶），本库 20 = 1.05M 桶（8 倍）。实测「桶内深度跨度/splat 尺度」：均匀 16 = 0.574、17 = 0.281、**20 = 0.030**、canvas 17 分位 = 0.059 ⇒ **20 均匀比 SuperSplat 实际配置细一倍**。⚠️ 本库排序在 **WASM 二进制**里（`sortIndexes`，无 C 源码），JS 只能传 `1<<precision` 一个标量，**做不了直方图分位**，要做得弃用 vendor 排序自己写。⚠️ 未来 4M+ splat 时 canvas 会自动升到 19–20 bit，本库被钳死 20 ⇒ 差距那时才显出来。
- ⚠️ 复现「远/中景才有」的渲染问题：**先把相机拉到用户实际观察距离**（脸 ~120px，d≈1.2）再测。近景 d≤0.55 时 splat 投影大、深度分布陡，量化误差打不乱可见顺序，**A/B diff 恒为 0**（本轮因此在错误候选上多绕很久）。
- **渲染参数基线 = SuperSplat 默认值**：`antialias:false / depth:false / stencil:false / powerPreference:'high-performance'`、`NoToneMapping + exposure 1`、fov 85（本页取 60）、`far 1000`、`halfPrecisionCovariancesOnGPU:false`、`setPixelRatio(devicePixelRatio)`。**故意不一致**：背景 `#222233`（纯黑糊掉暗部，峰哥拍板）。**库硬限**：SH bands 3→2、WebGPU→WebGL2、无 stochastic alpha。⚠️ `fitAllToFirst` 的固定距离 4 是按 fov 65 调的。

## splat-compare 内存释放链核查（峰哥问：删模型/重置后内存不显著下降，反复加删会不会爆）

**结论：不是泄漏，是四层「延迟归还」叠加；不会线性爆。** 两处小缺陷已记入 MEMORY.md。

释放链（已逐行走读）：
- `removePanel`（L339-348）：`p.viewer.dispose()`（= Viewer.dispose，库 L13932，**async、未 await**，finally 里才真正清）+ `p.renderer.dispose()` + `p.el.remove()` + splice。
- `loadPlyToPanel` 换模型（L471-477）：`splatGroup.dispose()` + `renderer.dispose()`。
- 库里 dispose 覆盖：SplatMesh geometry/material/**数据纹理**/splatTree（L10087-10178）、sortWorker **terminate**（L13779，WASM 随 worker 释放）、splatTreeWorker terminate（L9267）、controls/sceneHelper/renderer 引用清空。

不降的四个原因：
1. `renderer.dispose()`（three r185 L17068）**不调 forceContextLoss** —— WebGL context 要等 canvas 被 GC 才销毁，每个滞留 context 白占显存；快速反复加删可能撞 Chrome 单域 ~16 context 上限（最老被强丢→黑屏）。
2. V8 惰性 GC：大 TypedArray 变垃圾后要等 major GC，且堆页常保留在进程（RSS 不降）。
3. GPU 进程显存缓存，任务管理器看不到即时下降。
4. `Viewer.dispose()` 等 sortPromise settle 才 finally 清理（秒级延迟）。

真实缺陷（小）：
- ⚠️ 加载失败分支（catch, L718 起）**漏 `URL.revokeObjectURL(url)`**（成功路径 L717 有）→ 每失败一次漏一个文件大小的 blob。
- ⚠️ renderer 未 `forceContextLoss()`（见上）。

验证方法：DevTools Memory 手动 GC 后对比 heap snapshot；`performance.memory.usedJSHeapSize`；chrome://gpu。

## 补2：矩阵曝光模型的「亮粉/绿/蓝」伪彩（上一轮 AA 结论被推翻）

峰哥指出：真正症状是**发丝/眼睛/嘴角/衣服高光处出现亮粉、绿、蓝**，且只在「矩阵式曝光」重建的模型上，
SuperSplat 没有。⇒ 上一轮把蓝绿归因 `antialiased` 补偿是误判（AA 只会变淡透背景，产不出高饱和色）。

### 本轮排除的（都有实测，别再重走）
1. **SH 打包顺序**：vendor 内部布局是「按 band 分段 + 段内 channel-major」
   (band1 0-2/3-5/6-8，band2 9-13/14-18/19-23，band3 24-30/31-37/38-44)，
   与 `set3FromArray(stride, base)` 的 3/0、5/9、7/24 完全吻合。`degree3Fields` 也从 `i + 15*rgb + 8` 生成。**正确**。
2. **三纹理 SH 路径**（splat > 1,398,101 时触发，本机 712,847 永远走单纹理 —— 是测试盲区）：
   把 `if (shTexSize.x*shTexSize.y <= MAX_TEXTURE_TEXELS)` 改成 `if (false && ...)` 强制走三纹理，
   **画面与单纹理逐像素相同**。打包（t*3 / t*5+9 / t*7+24）与 shader 的 q0..q3 映射一致。
   ⚠️ 顺带发现：改 `MAX_TEXTURE_TEXELS` 会**连带把协方差降到 compressionLevel 1**，画面会偏紫 —— 不要拿它做 SH 的 A/B。
3. **上界 clamp**：把 L8077 `clamp(vColor.rgb, 0, 1)` 改成 `max(..., 0)`（对齐 PlayCanvas），
   截图**完全相同** —— 因为 framebuffer 最终会钳。所以「clamp 上界」不是可见差异来源。
4. **DC 预 clamp 的量级**：`tmp/dc_clamp_ab.py` 对比「先钳 DC 再加 AC」vs「DC+AC 后钳」，
   本机模型平均色差 0.0020、>0.25 仅 0.00%；mat2 模型 0.0079 / 0.05%。**不足以成片伪彩**。
5. 加压复现失败：AC×4/×8、饱和度矩阵 s=1.45/2.6 渲染都只有整体偏色+少量红斑，没有亮粉/绿/蓝斑块。

### 当前判断（未定论）
本库两处硬截断仍是最可疑的：解析期 `clamp((0.5+SH_C0*f_dc)*255, 0, 255)`（L3021，8bit 不可逆）
+ 顶点期 `clamp(rgb,0,1)`（L8077）；PlayCanvas 保留 f_dc float 原值、只 `max(clr,0)`。
本机模型 f_dc 已越界（rgb −1.20~2.01，19.1% splat 至少一通道越界），但 AC 很小（max|AC| p99.9=0.39），
所以截断影响被稀释。矩阵曝光模型很可能「DC 越界多 + AC 幅度大」同时成立才可见。
**要定论必须拿到那个 ply。**

### 顺带发现的真实 bug（未修，与本现象无关）
`gaussian-splats-3d.module.js:1706` 统计 SH 系数 min/max 时循环条件是
`sc < UncompressedSplatArray.OFFSET.FRC23`（=37），degree-3 的 band3 在 FRC 37..44 **没被纳入**。
只在 `compressionLevel === 2`（8bit SH）时才会让 band3 越界 wrap；当前 `getTargetSphericalHarmonicsCompressionLevel()`
= `Math.max(1, ...)` = 1（half float），不触发。修法：上界改 `FRC0 + shComponentCount`。

## 补3：为什么硬截断 + 对齐 SuperSplat 的 DC 颜色通路

峰哥问：PLY 解析和顶点上色两处为什么要硬截断，能否对齐 SuperSplat。

### 两处截断的真实来历（都是存储格式逼出来的，不是算法需要）
1. **解析期**（`INRIAV1PlyParser` 等 4 个解析器）：`FDC = (0.5 + SH_C0·f_dc) * 255` 再
   `clamp(floor(x), 0, 255)`。原因是下游存的是 **RGBA8**：`writeSplatDataToSectionBuffer`
   尾部 `const rgba = new Uint8ClampedArray(...)`，splatBuffer 每 splat 颜色 4 字节，
   打包进 `centersColorsTexture` 的 R 通道（RGBA32UI，center 的 float bits 占 GBA）。
   `Uint8ClampedArray` 本身也会钳，所以那行 clamp 只是把约束显式化 —— **删掉它并不能
   保住越界值**，必须换存储。
2. **顶点期**（`getVertexShader` 末尾）：`vColor.rgb = clamp(rgb, 0, 1)`。这条其实是
   针对 8-bit 通路写的语义补丁；PlayCanvas 是 `max(clr.xyz, 0.0)`，上界交给 framebuffer。

### SuperSplat 的真实对照（本轮查证）
`playcanvas/engine: src/scene/gsplat/gsplat-format.js` → `dataColor` 流是
**PIXELFORMAT_RGBA16F**（半浮点，默认格式和 simple 格式都是）；顶点 `gsplat.js` 结尾
`prepareOutputFromGamma(max(clr.xyz, 0.0), ...)`，linear tone mapping 下 gamma 是恒等。
⇒ 它是 **half float + 只钳下界**，本库是 **uint8 + 两端硬钳**。

### 本轮做法（8bit 内最优折中，非 100% 对齐）
- 4 个解析器统一改成存**线性颜色原值**（不 ×255、不 clamp）：PLY float、PLY codebook、
  SPZ（`((c/255-0.5)/COLOR_SCALE)·SH_C0+0.5`）、.splat（`inColor/255`）。
- 写 section 时 `encodeFDC(v) = clamp((v+0.5)*127.5, 0, 255)`，即区间 **[−0.5, 1.5]**。
- 顶点着色器 `vColor.rgb = vColor.rgb * 2.0 - 0.5` 解码；`clamp(...,1)` → `max(...,0)`。
- `SplatBuffer.CurrentMinorVersion` 0.1→0.2（`writeHeaderToBuffer` 里原本硬编码 1，
  一并改成引用常量），旧 .ksplat 直接被 `checkVersion` 拒绝而不是静默错色。
- 共 11 处 `LOCAL PATCH (fdc range)`。

⚠️ **中途踩的坑**：`fillSplatColorArray` 是**纹理数据源**（SplatMesh 用它填 colors 数组再
打包），我一度让它解码成线性值 ⇒ shader 再解一次 = 二次拉伸 ⇒ 满屏青绿/品红、对比度爆炸
（meanAbsDiff 26.6、83% 像素变化），一度以为"复现了用户的伪彩"。已改回：这两个读取 API
只返回**存储编码值**，解码只在 shader 里做一次。

### 验证
| 模型 | mean\|d\| | >阈值像素 | max |
|---|---|---|---|
| 原模型（19.1% splat 有通道越界） | 0.494 | 0.01% | 155 |
| mat2 强矩阵（43.9% 越界） | 0.859 | 0.28% | 31 |

`dc_clamp_ab.py`：单个 splat 的最大偏差可达 **0.56**（mat2 样例 DC=[1.63,0.62,0.10]，
旧版渲成 [0.44,0.80,0.48] 偏绿、新版 [1.0,0.80,0.48]），但平均只有 0.008 ——
即「极少数 splat 大幅偏色」，与峰哥描述的「发丝/眼角/高光处点状亮粉、绿、蓝」吻合。

回归：`check_splat_compare.js` 全过 / `verify_render_parity.js` 10/10 / `unify_semantics.js` 26/26
（中途两次 25/1 是 flaky，重跑即过）。

### 仍未做的（要 100% 对齐才需要）
把 splatBuffer 颜色 section 从 4 字节/ splat 改成 **RGBA16F（8 字节）**：要动
`CompressionLevels` 表、`bytesPerSplat` 计算、纹理（RGBA32UI 拆成独立 RGBA16F 纹理）、

## 补4：修 SH min/max 统计漏掉 degree-3 band-3（`LOCAL PATCH (sh range)`）

峰哥直接指定的这个 bug（上一轮我在报告里点出来的），本轮修掉。

### 上游缺陷（`generateFromUncompressedSplatArrays`，原 L1736）
```js
for (let sc = FRC0; sc < OFFSET.FRC23 && sc < splat.length; sc++)   // FRC0=14, FRC23=37
```
两处错：
1. **差一**：index 37 本身就是 band-2 的最后一个系数（FRC0+23），被排除；
2. **degree-3 的 band-3 在 index 38..58（21 个）完全没统计**。

后果只在 `compressionLevel === 2`（8-bit SH）时显形：`writeSplatDataToSectionBuffer`
里 `toUint8(v, min, max)` 用这对 min/max 做量化，漏掉的系数越界就被钳成 0/255
（该方向的高光/暗部直接丢），且**全程静默**。当前实跑 `getTargetSphericalHarmonicsCompressionLevel()`
= `Math.max(1, ...)` = 1（half float），所以是潜伏 bug，不是现症。

### 改法（2 处标记）
- 上界改 `sc < splat.length`（`splat.length = 14 + SH 分量数`，对 degree 1/2/3 都精确）。
- 顺带修 `!min / !max` 做「首次赋值」判断的 falsy 陷阱：值恰好为 0 时会被后续值错误覆盖，
  区间单边收窄 ⇒ 0 附近系数被量化到 0。改用 `=== undefined` 判断；配套的兜底也从
  `min || -halfRange` 改成显式 undefined 检查。
- 再加退化保护：min===max（所有系数相同）时区间宽为 0，`toUint8` 会除零得 NaN。
  以中点为心展开到默认半宽（全 0 时恰好还原上游默认 ±1.5）。

### 验证（`tmp/sh_range_fix.js` + 临时探针 `_pages/_shrange_probe.html`，已删）
构造 2 个 degree-3 splat：A 的 SH[44]（band-3 末）= 3.0，B 的 SH[24]（band-3 首）= −2.0，
band-1/2 全 0。用 `SplatBuffer.generateFromUncompressedSplatArrays` 直接生成 buffer 再读回：

| | min/max | lvl1（half）A/B | lvl2（8bit）A/B |
|---|---|---|---|
| 修前 | −1.5 / 1.5 | 3.0 / −2.0（正确） | **1.5 / −1.5（被钳）** |
| 修后 | −2 / 3 | 3.0 / −2.0 | **3.0 / −2.0（正确）** |

⇒ 证实「level 1 潜伏、level 2 掉值」，修复后 band-3 完整纳管。

### 顺带发现（未修）
`fillSphericalHarmonicsArray` 的输出压缩级别转换**缺 2→0 分支**（只有 1→0 / 1→2 / 0→1 / 0→2），
从 level-2 buffer 读 float SH 是 noop，拿到的是 0..255 原始量化值。当前渲染路径
`sphericalHarmonicsCompressionLevel = max(1, bufferLevel)` ≥ 1，不会走 2→0，故不影响页面。

### 回归

像素层面同机位重渲 mean|d| = 0.007、变化 0.01%（同代码两次重渲的噪声基线本身就是 0.003 / max 167）
⇒ 可视为零变化，与「level 1 不读这对 min/max」一致。

## 补5：补上相邻缺陷 —— 8-bit SH 的出口转换（`LOCAL PATCH (sh convert)`）

峰哥确认「颜色对齐改动已解决眼睛/嘴角/高光处的点状粉绿蓝」，**RGBA16F 那条不做了**。

### 缺陷 1（上游原有）：level-2 → float/half 全部 noop
`fillSphericalHarmonicsArray` 里 `outputConversionFunc` 只写了四路
（1→0、1→2、0→1、0→2），**没有 2→0 / 2→1** ⇒ 从 8-bit SH buffer 读出来是 0..255 的
原始量化整数（渲染时颜色会被放大 255 倍）。补 `localFromUint8` / `localFromUint8ToHalfFloat`。

### 缺陷 2（我 10-20 打 degree-3 补丁时引入）：band-3 在 transform 分支不解码
band-1（L1142）和 band-2（L1165）的 `if (transform)` 分支都会先
`toUncompressedFloatArray3(...)` 就地解码（因为此时 `compressionLevelForOutputConversion`
被强制置 0、出口是 noop），我写 band-3 时只做了 `copy3` ⇒
**level-1 源（页面实际在跑的级别）写出的是 half 位模式、level-2 源写出的是量化整数**。
补上 7 个 `toUncompressedFloatArray3`。
⚠️ 该缺陷只在 sceneTransform 非单位阵时触发；本页变换放 splatGroup 级（scene0 恒等），
所以页面一直没露馅 —— 又一个「潜伏 + 静默」型。
